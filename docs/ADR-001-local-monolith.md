# ADR-001: 采用本地单体架构

## 状态

已采纳

## 背景

PIM 的主要使用场景是个人部署、低运维成本、可在 macOS/Linux 本机直接运行。项目同时需要兼顾：

- 本地 SQLite 持久化
- 周期性抓取与简报生成
- React/Tauri 前端
- 尽量少的外部基础设施依赖

## 决策

采用以下默认架构：

- 数据库：SQLite
- API：FastAPI
- 定时任务：APScheduler
- 前端：React + Vite
- 桌面端：Tauri 作为可选壳层

## 原因

- SQLite 零运维，适合单用户和轻量部署
- FastAPI 同时兼顾异步接口、类型校验和自动文档
- APScheduler 足以覆盖本地定时抓取，不必引入 Redis/Celery
- 单体架构更便于个人项目维护与排障

## 结果与权衡

优点：

- 上手快，部署简单
- 本地运行资源占用低
- 问题定位路径短

代价：

- 横向扩展能力有限
- SQLite 并发写入上限低于服务型数据库
- 复杂后台任务编排能力不如专门的队列系统

## 触发重评估的条件

出现以下任一情况时，应重新评估是否拆分架构：

- 多用户并发写入显著增加
- 需要跨机器分布式任务执行
- 需要更强的审计、备份和 HA 能力
