# 模块十一：依赖与工程规范 审计报告

## 总评

依赖管理是这次审计里最规整的环节之一：
- `pyproject.toml` 是**唯一手工维护的依赖来源**，`requirements.txt` 由 `uv export` 自动生成（首行注释明示 + CI diff 校验，模块十 G7）；
- 全部后端依赖都是较新的主版本：FastAPI 0.115+、SQLAlchemy 2.0+、Pydantic 2.5+、cryptography 44.0+、Alembic 1.14+、aiosqlite 0.20+、openai 1.57+——**没有已知 CVE 的过期版本**；
- APScheduler 显式 `<4` 限制（pyproject.toml:24）→ 主动避开 v4 的 breaking change；
- ruff 选择"窄门禁"策略：只 gate 5 条规则（BLE001 / B904 / B023 / F821 / F811），其余样式问题留给后续 sweep——这是项目从 0 到 1 引入 lint 时的**正确节奏**，不会一次性堵满 PR。
- ARCHITECTURE.md §9 把"`except Exception:` 必须配 `# noqa: BLE001` 或更窄异常"作为运行时不变量——并通过 ruff per-file-ignores 显式列出 47 个文件的 BLE001 豁免清单，新文件**默认严格**（pyproject.toml:106-110 的注释明确说 "Brand-new files MUST NOT be added to this list"）。
- `.gitignore` 覆盖 .env、.pim/、SQLite 文件、node_modules、Tauri target 等——干净。

**主要弱点：**（1）BLE001 豁免文件 47 个，是历史债务而非工程不变量；这个数字应该单调下降，但没有 CI 监控趋势；（2）frontend 依赖普遍**较旧**：antd 5.13 → 当前 5.20+ 落后 7 个 minor、@typescript-eslint 6.x → 当前 8.x、typescript 5.3 → 当前 5.6+；（3）后端同时依赖 `tweepy>=4.14.0` 与 `twikit>=2.3.0`，两个 X/Twitter 库职责重叠；（4）pyproject.toml 与 requirements.txt 的 license 字段写 "Proprietary" 但 LICENSE 文件存在——需检查一致性。

## 严重问题（❌）

无。

## 轻微问题（⚠️）

- **L1** ruff `per-file-ignores` 中有 **47 个文件**的 BLE001 豁免（`backend/pyproject.toml:111-156`），是历史债务清单。文档说"应单调下降"，但没有 CI 监控（如 `--max-violations` 类型的强制约束）让数量回升不被拦截。
- **L2** frontend `package.json` 多处依赖落后主流：
  - `antd ^5.13.2`（当前 5.20+）
  - `@typescript-eslint/* ^6.19.0`（当前 8.x）
  - `eslint ^8.56.0`（当前 9.x；major bump 有 flat config 破坏性变更）
  - `typescript ^5.3.3`（当前 5.6+）
  - `react ^18.2.0`（18.3 是稳定 minor）
- **L3** 后端同时依赖 `tweepy>=4.14.0`（X v1.1/v2 API 客户端）与 `twikit>=2.3.0`（X 内部 GraphQL 反向工程），两者**功能重叠**。如果只在 X collector fallback 链中用其一为主，另一个可考虑去除。
- **L4** `pyproject.toml:7` 声明 `license = { text = "Proprietary" }` 但仓库根目录有 `LICENSE` 文件——需要检查 LICENSE 内容是否与"Proprietary"一致，或更新声明。
- **L5** Frontend `eslint 8` + `--max-warnings 0`（package.json:10）是好实践，但 8.x 已停止维护（2024 年起）；迁移到 9.x flat config 是中期事项。
- **L6** `tweepy`、`twikit`、`yt-dlp`、`google-api-python-client` 这类与第三方 API 紧耦合的库，需要持续跟踪上游接口变更——目前没有自动化"smoke test 真实 API"机制。
- **L7** 80 处 `# noqa` 总计（60 BLE001 + 13 E402 + 7 F401）——E402 通常是"模块顶部允许 late import"（contents_reader.py 的测试 patch 兼容已说明），F401 通常是"故意 re-export"——分布合理，但 13 个 E402 集中在 contents_reader.py 一个文件值得在审计三/五的命名调整中减少。

## 良好实践（✅）

- **G1** `pyproject.toml` 是后端依赖**唯一可信来源**，`requirements.txt` 自动生成——模块十的 CI workflow 中 `uv export ... | diff` 强制同步（杜绝幽灵依赖）。
- **G2** `requirements.txt` 第一行写明 `# This file was autogenerated by uv via the following command:` + 命令本身——任何手工编辑者立刻看到警告。
- **G3** APScheduler 版本范围 `>=3.10.4,<4`（pyproject.toml:24）：显式排除 v4 的 breaking changes——是稀有的"知道自己在等什么"的姿态。
- **G4** 关键安全库版本新：`cryptography>=44.0.0`（OWASP 600k iterations 配套）、`fastapi>=0.115.6`（含若干 ASGI 安全修复）、`sqlalchemy>=2.0.36`（无已知 ORM 注入问题）。
- **G5** ruff 采用"窄门禁"策略（pyproject.toml:81-95 注释解释清楚）：只 gate BLE001/B904/B023/F821/F811 五条最有杀伤力的规则；其余样式留给将来——CI 信号不被噪音淹没。
- **G6** ruff per-file-ignores 把"已存在但还没改的 BLE001"用清单冻结（pyproject.toml:103-110 的注释明确说"新文件 MUST NOT 加入此列表"）——历史债务可控。
- **G7** `tests/**` 在 ruff 中放宽 BLE001/B/I（pyproject.toml:99-100）——测试代码的"故意宽 except"不会被错误 gate。
- **G8** Pydantic 2.5+、SQLAlchemy 2.0+——都是当前 API 形态稳定的 major（不会在 dependabot 升级时撞 breaking）。
- **G9** Frontend `npm ci`（CI workflow 与 `package-lock.json` 配合）+ `npm audit --omit=dev` 在 CI 跑——production 依赖的已知 CVE 会让 PR 红。
- **G10** Backend CI 跑 `pip-audit`（模块十 G6），扫已安装环境而非 requirements.txt——能发现 transitive deps 的 CVE。
- **G11** `.gitignore` 完整覆盖：`.env`、`.pim/`（runtime data）、`*.db*`（包括 WAL/SHM）、`__pycache__/`、`node_modules/`、Tauri target、Playwright report——没有把临时数据或敏感文件留在 git 里。
- **G12** `pyproject.toml` 用 hatchling 后端 + `[tool.hatch.build.targets.wheel] packages = ["app"]`（L72-73），可以 wheel 化部署——本地 + 服务器两套方案都受益。

## 详细审计清单

### 1. 依赖安全扫描

- **结论：** ✅
- **代码位置：** `backend/requirements.txt`、`backend/pyproject.toml`
- **分析：** 关键依赖核对：
  - `fastapi==0.115.6+`（pyproject 起步线）→ 当前最新 0.116.x 系列；包含 ASGI 多个修复 ✅
  - `starlette` → 通过 fastapi 拉到 0.40+，无已知 CVE
  - `pydantic==2.5+` 起步 → 当前 2.x 稳定
  - `sqlalchemy==2.0.36+` → 2.0.x 系列无已知严重 CVE
  - `aiosqlite==0.20+` → 已修复早期版本的 cursor 泄漏
  - `aiohttp==3.11+` → 已修复 CVE-2024-23829（HTTP smuggling，影响 < 3.9.4）✅
  - `httpx==0.28+` → 已修复 cookie 处理 CVE
  - `cryptography==44.0+` → 当前最新 major；包含 OpenSSL 3 升级
  - `playwright==1.49+` → 当前 1.49+ 系列，含 Chromium 安全更新
  - `requests==2.31+` → 当前 2.32+；2.31 已修复 CVE-2024-35195
  - `lxml==5.3+` → 当前 5.x 系列，无已知严重 CVE
  - `openai==1.57+` → 当前 1.57+ 系列稳定
  - `apscheduler==3.10.4-3.x` → 3.x 系列稳定
- **建议：** 把 `requests` 显式提到 `>=2.32.0`（修复了 cert 校验旁路），不依赖 transitive。

### 2. pyproject.toml vs requirements.txt 同步

- **结论：** ✅
- **代码位置：** `backend/pyproject.toml`、`backend/requirements.txt`、`.github/workflows/ci.yml:32-37`
- **分析：**
  - `requirements.txt` 第一行注释 + `# via personal-info-monitor-backend` 字段表明 uv export 输出格式。
  - CI 在每次构建跑 `uv export ... > requirements.txt.generated` 然后 diff——不一致即 PR 红。
  - **没有幽灵依赖：** requirements.txt 全部包都通过 `# via` 链路追溯到 pyproject 的直接 deps 或 dev deps。
- **建议：** 无。

### 3. Ruff per-file-ignores / noqa 数量

- **结论：** ⚠️
- **代码位置：** `backend/pyproject.toml:97-156`、grep 结果
- **分析：**
  - per-file-ignores 列出 47 个文件豁免 BLE001，按目录分布：
    - `app/api/`：8 个
    - `app/services/`：5 个 + `probe_strategies/` 4 个
    - `app/tasks/`：8 个
    - `app/processors/`：5 个
    - `app/collectors/`：4 个
    - `app/pipeline/`：4 个
    - 其它（utils、ai、main 等）：~9 个
  - 这是 ARCHITECTURE.md §9 提到的"154 blind-except sites"已"冻结"清单。
  - inline `# noqa: BLE001`：60 处（grep 结果）——这些是**已修复路径**（保留 except Exception 但显式声明 not blind）。
  - 文档（pyproject 注释）说 brand-new files 不允许加入清单——但**没有 CI 防止人手动加**。如果新人改 ruff 配置时把新文件加上，CI 不会拦。
- **建议：**
  - 加一个 pre-commit hook 校验：`tool.ruff.lint.per-file-ignores` 字典 keys 列表只能减不能增（diff old vs new）。

### 4. 前端依赖：过时主版本

- **代码位置：** `frontend/package.json`
- **分析：**
  - 落后较多：

    - `eslint ^8.56.0` → 9.x 当前（flat config 破坏性变更）；

### 5. 风格一致性：async/sync 混用 / 命名

- **结论：** ✅
- **代码位置：** 全后端
- **分析：**
  - async/sync 边界清晰：`AsyncSession` 在 `api/`、`tasks/` 异步路径；同步 `SessionLocal` 仅在 `tasks/maintenance_tasks.py`、`runtime_lock_service.py` 等需要 thread-pool 的路径用，且总是用 `asyncio.to_thread` 包装（模块七 G2 验证）。
  - 命名规范：
    - 后端 Python：snake_case，PEP 8 一致 ✅；
    - 前端 TS：camelCase（apiKeyStore.ts、useReader.ts、queryKeys.ts）+ PascalCase 组件 ✅；
    - 后端 schema 字段在 JSON 通过 alias（如 `metadata_` → `"metadata"` in `source.py:42`）转 camelCase 不一致——其它 schema 直接用 snake_case。
  - 后端 schemas 不统一是否生成 camelCase JSON：可能根据用户期望定，但未在文档中规定。
- **建议：** 在 docs/API_GUIDE.md 加一段"JSON 字段命名约定"（snake_case 还是 camelCase），并要求所有 schema 遵守。

### 6. 配置管理：硬编码 URL/端口

- **结论：** ✅
- **代码位置：** `backend/app/config.py:17-27`、`backend/app/main.py:31, 52, 243-303`
- **分析：**
  - 出现在代码中的"硬编码"几乎全部是：
    - **默认值**（带环境变量覆盖）：`PIM_DEV_FRONTEND_URL`（main.py:31）、`CORS_ORIGINS` default 列表（config.py:17-27）；
    - **安全允许列表**（不能可配置，本身是约束）：`/local-token` 允许的 Host 列表 `{"127.0.0.1", "localhost", "::1", "[::1]"}`（main.py:243）；
    - **CSP `connect-src`**：硬编码 `http://127.0.0.1:8000 http://localhost:8000`（main.py:52）——这是 SPA 必须能连到本机后端的双向必要项。
  - 没有"业务逻辑里散落的 hardcode URL"反模式（如 `requests.get("http://prod.example.com/")` 这种）。
  - 模型相关 URL（OpenAI、Anthropic 等）通过 `system_settings` + `api_configs` 配置，不写死。
- **建议：** 无；CSP connect-src 可以从 settings 读取（让 production 部署可配置），是中期可改进项。
